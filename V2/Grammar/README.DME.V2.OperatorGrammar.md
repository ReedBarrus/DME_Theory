## 1. Purpose

This document defines the operator grammar of DME V2.

The Read / Write Topology document defines where movement can occur.

This document defines how lawful movement occurs.

Core distinction:

```text
Topology = where movement can occur.
Operators = how lawful movement occurs.
Receipts = what remains accountable.
Admissibility = what movement may proceed.
Authority = what consequence may persist.
Budget = how much movement can occur.
```

Operators are typed movements through configuration-attention topology.

They define how structures move between:

```text
source
structure
runtime
ledger
projection
decision
execution
feedback
retention
proof
authority
reference
canon
```

This document does not define full schemas.

It defines the conceptual operator hierarchy and the non-collapse laws that later schemas must preserve.

## 2. Core Thesis

```text
Operators are lawful transition functions over DME’s read/write topology.
```

They govern:

```text
what becomes exposed

```

Operators are the grammar by which configuration becomes active, addressable, consequential, retained, proof-loaded, and governed.

## 3. Operator Classes

DME V2 uses three operator classes.

```text
Class I — Phase / Geometry Operators
Class II — Support / Runtime Operators
Class III — Compound / Regime Operators
```

These classes are typed, but not metaphysically absolute.

They preserve the bridge between:

```text
geometric / phase movement
runtime support movement
symbolic / agentic / workflow commands
```

### 3.1 Class I — Phase / Geometry Operators

Class I operators describe primitive configuration-state movement.

They operate closest to field geometry, phase, locality, transition, relation, and release.

They are:

```text
Expose
Bound
Differentiate
Relate
Transform
Integrate
Release
```

### 3.2 Class II — Support / Runtime Operators

Class II operators are DME operational supports built from Class I movements.

They make topology navigable, comparable, projectable, recordable, reusable, and locally incorporable.

They are:

```text
Select
Compare
Project
Record
Echo
Accept
```

### 3.3 Class III — Compound / Regime Operators

Class III operators are workflow-level, regime-level, or interface-level compounds.

They are composed from Class I and Class II operators plus:

```text
admissibility
budget
authority
stake
receipts
retention
proof
governance
```

They include:

```text
Permit
Simulate
Execute
Prove
Consent
Authorize
Reference
Canonize
Translate
Repair
Contest
Revoke
Archive
Reconcile
```

Compression is intentionally not listed as a normal Class III operator.

It is a quarantined compound dynamic.

## 4. Class I — Phase / Geometry Operators

Class I operators describe the basic movements of configuration topology.

They are the deepest operator layer DME names explicitly.

---

## 4.1 Expose

### Definition

```text
Expose = make configuration available to a frame.
```

Expose moves configuration from latent, native, hidden, inaccessible, or unobserved status into availability.

```text
latent/native configuration
→ exposed configuration
```

### Examples

```text
source event becomes observable
file diff becomes available
runtime state is surfaced
ledger record is opened
projection state is shown
```

### Non-Claims

```text
exposed ≠ selected
exposed ≠ admitted
exposed ≠ true
exposed ≠ authorized
```

---

## 4.2 Bound

### Definition

```text
Bound = create locality, scope, edge, frame, container, or constraint region.
```

Bound establishes where a configuration is being considered.

```text
unbounded/open configuration
→ bounded/local configuration
```

### Examples

```text
scope a source family
bound a runtime region
declare a decision frame
limit a projection audience
create a proof scope
declare a revocation boundary
```

### Why Bound is not Select

```text
Bound creates locality.
Select allocates attention to a bounded region.
```

Bound is geometric.

Select is attentional.

### Non-Claims

```text
bounded ≠ selected
bounded ≠ isolated from context
bounded ≠ permitted
bounded ≠ proven
```

---

## 4.3 Differentiate

### Definition

```text
Differentiate = generate difference, gradient, contrast, variation, or change evidence.
```

Differentiate exposes how configuration varies.

```text
configuration
→ differential evidence
```

### Examples

```text
detect change over time
compute difference between states
identify contrast
surface gradient
detect anomaly
observe rupture
```

### Relation to Distinction

Differentiate does not create full distinction by itself.

A distinction requires support, lens, scope, and selectable status.

```text
differentiate → difference evidence
difference evidence + support + lens + scope → distinction
```

### Non-Claims

```text
difference ≠ meaningful distinction
variation ≠ rupture
change ≠ consequence
contrast ≠ proof
```

---

## 4.4 Relate

### Definition

```text
Relate = establish adjacency, correspondence, tension, dependency, mapping, or relation candidate between bounded configurations.
```

Relate forms possible relation topology.

```text
A + B
→ relation candidate
```

### Examples

```text
map source event to runtime state
relate error to file cluster
relate token handle to distinction region
relate agent action to consequence
relate proof trace to reference candidate
```

### Interference

Interference is not a primitive operator.

Interference is a runtime phenomenon that may arise when related configurations overlap, interact, phase-shift, or feed back.

```text
Relate + active field overlap + pressure dynamics
→ InterferenceTrace
```

### Non-Claims

```text
related ≠ identical
correlated ≠ causal
adjacent ≠ bound
mapping ≠ proof
```

---

## 4.5 Transform

### Definition

```text
Transform = move configuration through basis, lens, representation, scale, coordinate system, or state.
```

Transform changes how configuration is expressed or processed.

```text
configuration in basis A
→ configuration in basis B
```

### Examples

```text
waveform → spectrum
OS event → structural event object
language → operator packet
runtime topology → projection view
ledger trace → dashboard summary
```

### Loss

Every transform must preserve or declare:

```text
lens
basis
scope
preserved axes
omitted axes
loss
uncertainty
lineage
```

### Non-Claims

```text
transformed ≠ equivalent unless declared
translation ≠ lossless
basis change ≠ truth
representation ≠ source
```

---

## 4.6 Integrate

### Definition

```text
Integrate = incorporate, accumulate, or reconcile distributed inputs into an updated configuration state.
```

Integrate closes or updates configuration from multiple inputs.

```text
inputs / differentials / feedback / traces
→ updated configuration
```

### Examples

```text
integrate feedback into runtime state
integrate retained support into active topology
integrate consequences into coherence delta
integrate relation candidates into topology candidate
```

### Scale Warning

Integrate appears at multiple scales.

At Class I:

```text
Integrate = geometric/runtime incorporation.
```

At lifecycle scale:

```text
Consequence Integration = compound process using Record, Compare, Integrate, Reconcile, Accept, or Release.
```

### Non-Claims

```text
integration ≠ self-authorization
integration ≠ truth
integration ≠ canon
feedback_integration ≠ legitimacy
```

---

## 4.7 Release

### Definition

```text
Release = remove, decay, loosen, exit, defer, archive, quarantine, or lower active constraint / budget.
```

Release is the lawful exit operator.

```text
bound / active / retained structure
→ released / decayed / deferred / quarantined structure
```

### Examples

```text
release stale runtime branch
decay projection
defer proof route
archive inactive record
quarantine unstable attractor
lower retention budget
remove execution handle
```

### Why Release Matters

Without release, recursion becomes runaway.

Release prevents:

```text
infinite recursion
attention capture
retention contamination
projection overload
authority inflation
```

### Non-Claims

```text
release ≠ deletion necessarily
archive ≠ active memory
quarantine ≠ invalidation
decay ≠ falsehood
```

## 5.6 Accept

### Definition

```text
Accept = take a candidate into a declared substrate, regime, projection, ledger, retention state, or local context under scope and receipt.
```

Accept is local incorporation.

```text
candidate
→ accepted local status
```

### Built From

```text
Bound + Record + admissibility/budget conditions
```

### Examples

```text
accept a projection into active dashboard state
accept a retained trace as runtime support
accept a consequence receipt into ledger
accept a proof trace as support
accept a reference candidate into review
```

### Why Accept Replaces Commit

Commit is reserved for agentic/behavioral dynamics such as sustained commitment to goals, decisions, or consequences.

Accept is more neutral and less likely to imply finality.

### Non-Claims

```text
accept ≠ truth
accept ≠ proof
accept ≠ authority
accept ≠ canon
accept ≠ permanence
accept ≠ behavioral commitment
```

## 6. Class III — Compound / Regime Operators

Class III operators are workflows built from Class I and II operators, plus admissibility, budget, authority, stake, receipts, retention, proof, and governance.

They are the operators most likely to appear in user interfaces, dashboards, LLM commands, and agent workflows.

---

## 6.1 Permit

### Definition

```text
Permit = allow a candidate transition to proceed under admissibility, scope, budget, authority, and receipt conditions.
```

Permit is the compound operator corresponding to DME’s transition-permission logic.

### Relation to Admissibility

```text
Admissibility = general transition-permission field.
Permit = compound operation that allows a transition to proceed.
```

### Relation to Admission

Admission is a specialized permit process.

```text
Admit = Permit entry into a substrate or regime.
```

Admission remains useful vocabulary in the Structure Substrate, but Permit is the more general compound operator.

### Example Operator Path

```text
Expose candidate
→ Bound scope
→ Select candidate
→ Compare constraints
→ evaluate admissibility
→ Permit transition if conditions pass
→ Record permission / denial / limitation
```

### Non-Claims

```text
permit ≠ authority
permit ≠ consent
permit ≠ proof
permit ≠ permanence
permission_to_move ≠ permission_to_create_unbounded_consequence
```

## 7. Compression Quarantine

Compression is not a normal operator in this grammar.

It is a quarantined compound dynamic.

### 7.1 Definition

```text
Compression = reduction of representational complexity under declared preserved invariants, omitted axes, lens, loss, lineage, and reconstruction limits.
```

Compression can occur through operator paths such as:

```text
Bound
→ Select
→ Transform
→ Release omitted axes
→ Project compressed view
→ Record loss profile
```

### 7.2 Why Compression is Quarantined

Compression is powerful but dangerous.

It can collapse:

```text
support
lineage
lensing
uncertainty
stake
identity
context
authority boundaries
```

DME permits compression only when it declares:

```text
preserved invariants
omitted axes
loss profile
scope
lineage
projection lens
reconstruction limits
non-claims
```

### 7.3 Core Law

```text
No compression without declared preservation and loss.
```

### 7.4 Non-Claims

```text
compression ≠ truth
compression ≠ neutral representation
compression ≠ proof
compression ≠ canon
compressed ≠ complete
```

## 8. Receipts and Provenance Conservation

Operators must preserve provenance without producing infinite receipt noise.

DME distinguishes:

```text
OperatorTrace
ProvenanceEnvelope
Receipt
```

### 8.1 OperatorTrace

```text
OperatorTrace = local trace of one or more operator applications inside a bounded span.
```

Operator traces may remain internal to a pipeline.

### 8.2 ProvenanceEnvelope

```text
ProvenanceEnvelope = conserved lineage, lens, loss, scope, and authority context across a meaningful transition.
```

Every accountable transition must preserve a provenance envelope.

### 8.3 Receipt

```text
Receipt = ledgered accountability object emitted when a transition changes what may be remembered, projected, executed, trusted, authorized, or used as reference.
```

### 8.4 Receipt Trigger Conditions

A receipt is required when movement:

```text
crosses substrate boundary
changes retention state
creates or updates a projection handle
emits consequence
introduces declared loss
runs a proof/load test
changes access
changes authority
creates reference/canon posture
archives, revokes, or quarantines an object
```

### 8.5 Receipt Law

```text
Receipts are not logs of every movement.
Receipts are accountability anchors for meaningful boundary transitions.
```

Low-level operations may be grouped into operator spans.

Example:

```text
Structural admission span:
Expose + Bound + Differentiate + Transform + Relate
→ one StructuralAdmissionReceipt
```

Not every micro-operation needs its own receipt.

## 9. Operator Spans

An OperatorSpan is a bounded sequence of operators acting toward a declared transition.

### Definition

```text
OperatorSpan = ordered group of operator applications under a shared scope, lens, budget, and provenance envelope.
```

Operator spans prevent receipt explosion while preserving topological provenance.

### Example

```text
Projection span:
Select runtime region
→ Compare active relations
→ Project dashboard view
→ Record projection receipt
```

### Span Requirements

An operator span must declare:

```text
purpose
scope
operators used
inputs
outputs
lens
loss
authority ceiling
receipt trigger
provenance envelope
```

No formal schema is required yet.

## 11. Operators and Read / Write Topology

Operators must preserve the distinction between read-side and write-side topology.

### Read-Side Operators

Primarily expose, bound, differentiate, relate, transform, select, compare, project, record.

Read-side movement asks:

```text
What can be seen, distinguished, compared, and addressed?
```

### Write-Side Operators

Primarily select, permit, accept, execute, integrate, release, authorize, revoke.

Write-side movement asks:

```text
What can be attended, intended, emitted, integrated, authorized, or released?
```

### Coupling Operators

Projection, Record, Echo, Integrate, and Reconcile couple read-side and write-side dynamics.

Core law:

```text
Projection mediates reading.
Execution mediates writing.
Integrate closes feedback.
Record preserves accountability.
Release prevents runaway recursion.
```

## 12. Operators and Regime Boundaries

Regime transitions are operator-bounded.

A regime change must answer:

```text
What operator path moved this candidate?
What substrate boundary was crossed?
What was preserved?
What was lost?
What was recorded?
What was permitted?
What authority ceiling applied?
```

Examples:

```text
Configuration becomes distinction through:
Expose + Bound + Differentiate + Compare

Distinction becomes projection handle through:
Project + Record

Projection becomes language packet through:
Transform + Project

Decision branch becomes execution candidate through:
Select + Permit + Accept

Execution becomes consequence through:
Execute + Record

Consequence becomes future topology through:
Record + Compare + Integrate

Candidate becomes proof-supported through:
Prove + Record

Authority becomes reference through:
Authorize + Reference + Record

Reference becomes canon through:
Canonize + governance review + revocation path
```
