## 1. Purpose

This document defines the core architecture of DME V2.

It translates the Theory Foundation into a compressed architectural skeleton.

The Theory Foundation answers:

```text
What must the system preserve?
```

This Core Architecture answers:

```text
How is the system structured?
```

DME V2 is organized around four primary substrates:

```text
Structure
Runtime
Ledger
Projection / Index / Rasterization
```

All other regimes are lifecycle dynamics, operator paths, constraints, or object ecologies distributed across these four substrates.

This document intentionally avoids exhaustive schema.

Formal schemas are deferred until the conceptual architecture stabilizes.

---

## 2. Core Compression

DME V2 can be compressed into the following architecture:

```text
Structure exposes configuration.
Runtime activates distinction.
Ledger records causal continuity.
Projection rasterizes topology into addressable handles.
```

The main loop:

```text
source emission
→ structural admission
→ distinction formation
→ runtime attention
→ topology / decision / intention
→ projection / execution
→ consequence
→ feedback
→ integrate
→ ledger / retention / proof / authority / reference
→ future recursion
```

DME is therefore not merely a memory system.

DME is a system for preserving and governing configuration continuity across source, runtime, record, and projection.

---

## 3. Architecture Thesis

```text
DME is a four-substrate configuration-attention architecture
for converting source-derived structure into active distinction,
accountable memory, bounded consequence, and revocable reference.
```

DME does not assume that:

```text
stored data = memory
projection = truth
salience = importance
recurrence = proof
trust = authority
execution = legitimacy
canon = final truth
```

Instead, DME preserves the transitions between these states so that each can be inspected, bounded, challenged, retained, released, or governed.

## 4. The Four Substrates

## 4.1 Structure Substrate

### Function

```text
Structure exposes source-native configuration.
```

The Structure Substrate receives source emissions and converts them into lawful structural objects that can support distinctions.

It answers:

```text
What source material exists?
Under what lens can it be exposed?
What structure can be lawfully extracted?
What distinctions can be supported?
What uncertainty and loss were introduced?
```

### Typical inputs

```text
audio waveform
JSON object
tool call
OS runtime event
file diff
language emission
sensor trace
model response
database row
institutional record
```

### Typical outputs

```text
NativeEmission
PayloadRef
StructuralObject
Chart
StructuralSignature
Feature
DistinctionEvidencePacket
DistinctionRegion
```

### Boundary law

```text
Structure is not meaning.
Structure is not memory.
Structure is not authority.
Structure only exposes configuration that may support distinction.
```

```text
Runtime activates distinction under attention.
```

It is where attention, salience, interference, relation, decision pressure, and attractor dynamics form.

It answers:

```text
What is active now?
What distinctions are interacting?
Where is attention accumulating?
Where are relations forming?
Where are branches becoming possible?
Where are attractors stabilizing or rupturing?
```

### Typical inputs


### Boundary law

```text
Runtime may form candidates.

Runtime does not produce proof, authority, canon, or final meaning by itself.
```

## 5. Substrate Relationship

The four substrates form a loop, not a hierarchy of value.

```text
Structure → Runtime → Ledger → Projection → Runtime
```

More fully:

```text
Structure exposes possible distinction.
Runtime activates and evolves distinction.
Ledger records what became causally accountable.
Projection makes selected topology addressable to agents, tools, users, and future runtime.
```

Projection may influence runtime because what is exposed changes attention.

Ledger may influence runtime through retention and echo.

Runtime may influence ledger through events, receipts, and consequence.

Structure may influence projection through source-derived evidence.

The system remains lawful only if these influences are mediated by operators, budgets, admissibility, projection boundaries, and receipts.

## 6. Core Runtime Loop

The operational loop:

```text
1. Source emits.
2. Structure admits and exposes configuration.
3. Distinctions form.
4. Runtime activates distinctions under attention.
5. Relations, branches, and attractors form.
6. Projection rasterizes active topology into handles/views.
7. Agents or users read projections.
8. Language/operator packets modulate attention and decision pressure.
9. Decisions form and intention accumulates.
10. Admissibility and consent evaluate transition permission.
11. Execution emits bounded consequence.
12. Feedback returns from the target regime.
13. Integrate reconciles consequence with feedback.
14. Ledger records the causal path.
15. Retention determines persistence and echo.
16. Proof tests candidates requesting escalation.
17. Budget, trust, access, authority, and reference are modulated.
18. Future runtime begins with altered configuration.
```

This loop is the basic DME metabolism.

## 7. Read / Write Topology

DME distinguishes read-side and write-side dynamics.

### 7.1 Read-Side Configuration Topology

Read-side topology concerns what can be observed, distinguished, mapped, projected, queried, or compared.

```text
source
→ structure
→ distinction
→ projection
```

It asks:

```text
What is present?
What can be distinguished?
What can be exposed?
What is the system able to see?
```

### 7.2 Write-Side Attentional Topology

Write-side topology concerns what becomes weighted, pressurized, selected, emitted, retained, or authorized.

```text
attention
→ intention
→ execution
→ consequence
→ integrate
```

It asks:

```text
What is becoming active?
What is becoming action-bearing?
What consequence is forming?
What feedback returns?
What future budget changes?
```

### 7.3 Coupling Law

```text
Projection mediates reading.
Execution mediates writing.
Integrate closes the feedback loop.
Ledger records both.
Runtime dynamically couples both.
```

## 8. Operators as Boundary Grammar

Operators define lawful movement between substrates and regimes.

Core operators:

```text
Expose
Select
Transform
Compare
Project
Record
Echo
Commit
Release
Integrate
```

Operators answer:

```text
What moved?
From where?
To where?
Under what lens?
What was preserved?
What was lost?
What was recorded?
What may re-enter?
What must release?
What feedback was integrated?
```

Operators prevent regime collapse.

Examples:

```text
Project prevents runtime topology from pretending to be source.
Record prevents consequence from disappearing without lineage.
Echo prevents memory from re-entering without scope.
Integrate prevents feedback from becoming self-authorizing.
Release prevents recursion from becoming infinite.
```

## 9. Runtime Regime Lifecycle

DME regimes are lifecycle dynamics across the four substrates.

They are not all primary substrates.

A compressed lifecycle:

```text
Distinction
→ Expectation
→ Belief
→ Decision
→ Intention
→ Projection
→ Consent / Admissibility
→ Execution
→ Consequence
→ Feedback
→ Integrate
→ Retention
→ Proof
→ Budget / Trust / Access / Authority
→ Reference
→ Canon
```

### 9.1 Distinction

Supported difference in configuration space.

### 9.2 Expectation

Anticipated recurrence.

### 9.3 Belief

Retained expectation topology associated with an agentic locus.

### 9.4 Decision

Branchable transition topology over admissible distinctions.

### 9.5 Intention

Budgeted write-side attention over decision topology.

### 9.6 Projection

Bounded rasterization of topology into addressable view-space.

### 9.7 Consent / Admissibility

Permission dynamics governing whether transition or consequence is allowed.

Admissibility is the general transition-permission field.
Consent is a specialized agentic admissibility relation involving loci of agency, stake, consequence, and revocation.

### 9.8 Execution

The crossing where a decision branch emits effect into a target regime.

### 9.9 Consequence

Realized decision topology after execution.

### 9.10 Feedback

Return signal from the target regime.

### 9.11 Integrate

Operator that reconciles consequence with feedback and updates future configuration.

### 9.12 Retention

Persistence, decay, archive, quarantine, and echo eligibility.

### 9.13 Proof

Survival testing under load and budget escalation filter.

### 9.14 Authority

Scoped consequence capacity.

### 9.15 Reference

Stabilized authority-bearing configuration that may guide future processing.

### 9.16 Canon

Governed, durable, revocable reference geometry.

## 10. Projection, Tokens, Embeddings, and Symbols

Projection is central because it makes DME usable by humans, LLMs, agents, tools, and dashboards.

### 10.1 Tokens

```text
Tokens = discrete projection handles.
```

Tokens make topology addressable.

They are not distinctions by themselves.

### 10.2 Embeddings

```text
Embeddings = coordinate lenses over projected handles.
```

Embeddings provide navigable neighborhoods.

They are not meaning by themselves.

### 10.3 Symbols

```text
Symbols = stable topological compressions of distinction, relation, use, memory, and consequence.
```

Symbols are not raw tokens.

A SymbolObject is a stabilized handle/distinction/relation binding that has survived sufficient transformation, feedback, or proof within scope.

### 10.4 Language

Language can function as operator grammar over projected topology.

A prompt can become a LanguageOperatorPacket that modulates:

```text
attention
selection
projection
decision pressure
intention
execution proposals
retention requests
proof requests
governance requests
```

Language does not directly authorize consequence.

## 11. Decision Space and Consequence

Decision space is where many of the most important dynamics converge.

Decision space includes:

```text
possible branches
rejected branches
simulated branches
intention pressure
execution candidates
realized branches
consequences
feedback
authority curvature
```

Execution does not require a separate universe.

Execution is the moment a decision branch crosses from projected possibility into target-regime effect.

Consequence does not require a full peer substrate.

Consequence is the realized topology of executed decision.

The ledger records executed decisions as causal history.

## 12. Budget and Authority

Budget is the dynamic expression of constraint.

```text
Constraint defines lawful boundary.
Budget meters movement through boundary.
```

Budget governs:

```text
attention
projection
rasterization
runtime processing
retention
proof
execution
governance
access
ledger recording
```

Authority is budgeted consequence capacity.

```text
Authority = scoped, revocable consequence capacity.
```

Authority is earned through:

```text
coherent execution history
feedback
trust evidence
stake accounting
proof where required
constraint preservation
revocation path
```

Authority may become reference only when its use stabilizes into future guidance under scope.

Reference may become canon only through governance and revocation conditions.
