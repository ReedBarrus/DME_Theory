## 1. Purpose

This document defines the Projection / Index / Rasterization Substrate of DME V2.

Projection / Index / Rasterization is the governed address layer of DME.

It explains how active runtime topology, ledger history, structural distinctions, decision space, agentic loci, proof traces, retention records, and authority states become:

```text
addressable
queryable
navigable
tokenized
embedded
symbolized
displayable
LLM-readable
dashboard-readable
tool-targetable
agent-accessible
```

Projection is not merely display.

Projection is the dangerous bridge between reality-coupled runtime and symbol-coupled action.

This document defines how DME makes topology legible without allowing projection to become source, proof, truth, authority, or canon.

## 2. Core Thesis

```text
Projection / Index / Rasterization is the governed address layer of DME.

It turns active runtime and ledger topology into handles, tokens, embeddings, symbols, packets,
dashboards, and coordinate views while preserving provenance, declaring loss, and preventing
projection from becoming source, proof, authority, or truth.
```

Compressed:

```text
Runtime coordinates carry active topology.
Projection coordinates make topology addressable.
Index coordinates projected handles.
Rasterization converts topology into usable handles.
Provenance preserves accountable identity through projection.
Arbitration determines which projection basis may influence consequence.
```

## 3. Why Projection Exists

Runtime topology is rich but not inherently legible.

Runtime contains:

```text
active distinctions
attention gradients
relation candidates
field pressure
decision branches
intention gradients
interference traces
retention echoes
proof tensions
authority constraints
```

Humans, LLMs, agents, tools, dashboards, and governance surfaces cannot directly use the full runtime continuum.

They require bounded views.

Projection exists to create those bounded views without collapsing the view into the thing viewed.

Projection answers:

```text
What can be seen?
Through what lens?
At what resolution?
By whom or what?
For what use?
With what omissions?
With what authority ceiling?
With what provenance?
With what permitted response handles?
```

## 4. Projection, Index, and Rasterization

These terms are related but distinct.

### 4.1 Projection

```text
Projection = bounded rasterization of internal topology into addressable view-space.
```

Projection produces a view under a declared lens.

### 4.2 Index

```text
Index = navigable address layer over projected handles and their relations.
```

Index routes, locates, relates, and retrieves projected topology.

### 4.3 Rasterization

```text
Rasterization = conversion of dynamic topology into addressable handles without pretending the handles are the topology itself.
```

Rasterization turns active field complexity into usable surfaces.

### 4.4 Combined Function

```text
Projection creates bounded views.
Index connects and routes them.
Rasterization gives them handles.
```

Projection should be used when active topology requires one or more of the following:

```text

cross-basis comparison
```


## 8. When Projection Should Be Resisted

Projection is not neutral.

Projection creates handles, and handles attract attention.

Projection should be resisted, delayed, narrowed, or quarantined when:

```text
runtime region is unstable
distinction support is weak
projection would over-stabilize a fuzzy attractor
loss profile cannot be declared
provenance envelope is incomplete
audience does not need access
projection would create harmful salience
object is not permitted for exposure
consequence tier exceeds proof or authority posture
projection would collapse multiple bases into one view
```

Core warning:

```text
Projection can stabilize.
Projection can distort.
Projection can over-authorize.
Projection can create false symbolic reality.
```

### 11.2 ProjectionObject

```text

omitted axes
```

### 11.3 ProjectionHandle

```text
ProjectionHandle = addressable pointer into projected topology.
```

A handle allows the system to refer to a bounded projected region.

A handle is not the topology.

```text
handle ≠ object
handle ≠ distinction
handle ≠ truth
```

### 11.4 ProjectionToken

```text
ProjectionToken = discrete symbolic handle over projected topology.
```

ProjectionTokens may be linguistic, symbolic, JSON-oriented, UI-oriented, or internal.

Examples:

```text
"build_failure"
"runtime_pressure"
"decision_branch_03"
"proof_trace_A"
"authority_ceiling_local"
```

A token is a handle.

It is not a distinction by itself.

### 11.5 EmbeddingRegion

```text
EmbeddingRegion = coordinate neighborhood over projection handles or tokens.
```

Embedding regions support:

```text
retrieval
semantic adjacency
cluster discovery
query routing
LLM context construction
drift detection
symbol candidate formation
```

EmbeddingRegion is not meaning.

Embedding proximity is not identity.

### 11.6 SymbolCandidate

```text
SymbolCandidate = recurring handle/distinction/relation pattern that may stabilize into symbolic topology.
```

A SymbolCandidate forms when projected handles begin to recur across contexts.

SymbolCandidate is not proof.

SymbolCandidate is not canon.

### 11.7 SymbolObject

```text
SymbolObject = proof-supported symbolic topology that preserves functional invariance across declared transformations.
```

A SymbolObject may become useful for:

```text
language coupling
decision support
reference formation
operator targeting
agent coordination
human interpretation
```

SymbolObject is still scope-bound.

### 11.8 ReferenceSymbol

```text
ReferenceSymbol = authority-bearing symbol that may guide future configuration under declared scope.
```

ReferenceSymbol is not universal truth.

### 11.9 CanonicalSymbol

```text
CanonicalSymbol = governed, durable, revocable reference symbol.
```

CanonicalSymbol is not final truth.

Canon must remain revocable.

## 13. Projection Basis Arbitration

Projection creates many coordinate regimes over one runtime continuum.

No projection basis may govern consequence by itself.

### 13.1 Definition

```text
Projection Basis Arbitration =
the process of deciding which projection basis may influence attention, decision,
execution, retention, proof, authority, or reference under current scope.
```

It does not choose the one true basis.

It chooses which basis may matter for this purpose, at this consequence tier, under this scope.

### 13.2 Basis Types

Projection bases may include:

```text
structural basis
runtime topology basis
ledger basis
projection handle basis
token basis
embedding basis
decision basis
agentic basis
retention basis
proof basis
authority basis
reference basis
```

### 13.3 Basis Claims

Each basis makes a different kind of claim.

```text
structural basis:
the source supports this distinction

runtime basis:
this topology is active now

ledger basis:
this causal path was recorded

projection basis:
this topology is addressable under this lens

embedding basis:
these handles are near under this coordinate lens

decision basis:
this branch matters for possible consequence

proof basis:
this survived declared load

authority basis:
this may affect consequence within scope

reference basis:
this may guide future interpretation
```

All may be valid.

None is sovereign alone.

### 13.4 Arbitration Stack

When bases compete, DME evaluates:

```text
scope
provenance
fidelity
recency / feedback
cross-basis support
proof posture
stake
authority ceiling
budget
reversibility
integration result
```

### 13.5 Core Law

```text
A projection basis may influence consequence only to the degree that its scope,
provenance, fidelity, proof posture, stake alignment, and authority ceiling support.
```

Budget meters influence.

Admissibility gates transition.

Authority gates consequence.

Proof tests basis fidelity.

Stake prevents externalized harm.

Provenance preserves identity.

## 14. Projection Fidelity

### Definition

```text
Projection Fidelity =
the degree to which a projection preserves the structural, relational, temporal,
provenance, and consequence-relevant axes required by its declared use.
```

Projection fidelity is use-bound.

A projection may be high-fidelity for one use and low-fidelity for another.

Example:

```text
"3 failing tests"
```

High-fidelity for status overview.

Low-fidelity for repairing the bug.

Projection fidelity depends on:

```text
declared lens
declared purpose
consequence tier
needed axes
resolution
omitted axes
reconstruction path
```

Core law:

```text
Projection fidelity is evaluated relative to use, not globally.
```

## 15. Provenance Fidelity

### Definition

```text
Provenance Fidelity =
the degree to which a projected object preserves or references the lineage, lens, loss,
source, operator path, authority ceiling, and reconstruction conditions of the topology it represents.
```

A projection with weak provenance cannot be allowed to drive high consequence.

```text
weak provenance → low consequence tier
strong provenance → higher proof/decision utility
```

Every projection handle should preserve or reference a ProvenanceEnvelope.

### 15.1 ProvenanceEnvelope

```text
ProvenanceEnvelope =
the conserved lineage/lens/loss/scope/authority container that allows a structure
to transform, project, compress, echo, execute, or re-enter without losing accountable identity.
```

Short form:

```text
Provenance is identity conservation through transformation.
```

### 15.2 Projection Provenance Law

```text
Every projection handle must preserve or reference a provenance envelope.
```

No handle should float without lineage.

No token should detach from lens.

No embedding region should hide loss.

## 16. Feedback Reconciliation Into Projection

New feedback regions must not be dumped into the continuum.

They must be reconciled.

### 16.1 Feedback Reconciliation

```text
Feedback reconciliation =
the process by which a new local feedback region is bounded, compared, related,
projected, recorded, and integrated into existing attention-configuration topology
without collapsing locality, lens, or provenance.
```

### 16.2 Feedback Entry Path

```text
Expose feedback
→ Bound locality and source family
→ Differentiate against expectation or consequence
→ Relate to existing handles, records, decisions, and source structures
→ Compare across relevant bases
→ Detect alignment, rupture, recurrence, or novelty
→ Permit appropriate runtime / projection / retention entry
→ Project bounded handles if useful
→ Record provenance envelope / receipt if boundary-worthy
→ Integrate coherence delta into runtime, retention, budget, proof, access, authority
```

This is bounded reconciliation, not global absorption.

## 17. Projection and Proof

Proof should leverage projection cross-basis.

Projection is not proof, but projection creates proof targets.

Proof may test:

```text
does this token still point to the same distinction region?
does this embedding neighborhood preserve structural relation?
does this projection omit an axis needed for consequence?
does this decision branch remain valid under source-basis comparison?
does this symbol survive translation, paraphrase, execution, and feedback?
does this authority claim remain scoped when projected into another regime?
```

This is:

```text
cross-basis fidelity testing
```

Projection makes many coordinate bases visible.

Proof tests whether those bases remain faithful under load.
