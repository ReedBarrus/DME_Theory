---

## 1. Purpose

This document defines how DME/RIFT conceptual development should proceed during architecture compression.

It treats conceptual work itself as a DME process:

```text
conversation produces emissions
emissions form distinctions
distinctions accumulate attention
attention creates decision pressure
decisions produce architecture changes
architecture changes create consequences
consequences are integrated only when they preserve invariants and increase coherence
```

The purpose is to prevent the architecture from expanding into unbounded regimes, schemas, and documents before the conceptual skeleton is stable.

This document governs:

```text
how new concepts are admitted
how concepts are located
how concepts are compressed
how conflicts are handled
how decisions are made
how docs are updated
how old docs are archived
how schema elaboration is deferred
```

---

## 2. Core Thesis

DME conceptual development must follow the same principles as DME runtime:

```text
distinguish carefully
budget attention
preserve lineage
avoid collapse
compress by invariant survival
integrate only coherence-regenerating structures
release what no longer carries active value
```

Compression is not deletion.

Compression is invariant preservation under reduced representation.

## 4. Workflow Loop

Every conceptual cycle should follow this loop.

### 4.1 Emit

A concept, question, analogy, contradiction, concern, or proposal appears.

Examples:

```text
tokens are handles
projection is rasterization
authority is consequence budget
belief is retained expectation topology
consent is admissibility between agentic loci and consequence-bearing decisions
```

### 4.2 Distinguish

Identify the actual difference the concept introduces.

Ask:

```text
What new distinction does this create?
What confusion does it resolve?
What previous category does it split, merge, or mutate?
What does it prevent from collapsing?
```

### 4.3 Locate

Place the concept inside the architecture.

Allowed locations:

```text
substrate
regime
lifecycle object
operator
constraint
budget dynamic
projection handle
ledger record
example
non-collapse law
implementation wedge
deferred concept
```

If the concept cannot be located, do not create a new regime immediately.

First test whether it can be represented as:

```text
substrate behavior
operator behavior
lifecycle object
regime sub-dynamic
projection/index handle
budget/constraint effect
```

### 4.4 Compare

Compare the concept to existing concepts.

Classify it as:

```text
duplicate
refinement
mutation
contradiction
new object
new operator
new regime candidate
new substrate candidate
archive candidate
```

### 4.5 Compress

Reduce the concept to the smallest invariant expression.

Ask:

```text
What is the minimum sentence that preserves the distinction?
What is the minimum object sketch?
What must survive paraphrase?
What can be safely demoted?
What can be merged?
```

### 4.6 Budget

Determine how much attention and document-space the concept deserves.

Budget classes:

```text
one-line glossary entry
non-collapse law
example only
paragraph in existing doc
object sketch
section in existing doc
regime subsection
full regime doc
core architecture anchor
deferred / archived
```

### 4.7 Decide

Choose one of the following actions:

```text
preserve
merge
mutate
promote
demote
defer
archive
delete
```

The decision must name the consequence for the architecture.

### 4.8 Integrate

Update the relevant map, doc, section, or anchor.

Integration requires:

```text
lineage preserved
concept placed
non-claims declared where needed
collapse risk reduced
architecture coherence increased
```

### 4.9 Release

Explicitly release concepts that no longer need active attention.

Release does not mean deletion.

Release may mean:

```text
archived
merged
demoted
deferred
example-only
glossary-only
kept as historical source
```

## 5. Compression Laws

### 5.1 No New Regime Without Burden

No new regime should be created unless the concept cannot be represented as:

```text
substrate behavior
operator behavior
lifecycle object
regime sub-dynamic
projection/index handle
budget/constraint effect
```

A new regime must answer:

```text
What dynamics does this regime uniquely explain?
What does it prevent from collapsing?
What substrate faces does it span?
What objects belong to it?
What operators move into or out of it?
What is its read-side configuration topology?
What is its write-side attentional topology?
What is its authority ceiling?
```

### 5.2 No New Document Without Consequence

No new document should be created unless it:

```text
protects a major invariant
prevents repeated confusion
compresses multiple old docs
defines a substrate
defines a core grammar
defines a major regime ecology
anchors implementation strategy
```

If a concept can live as a section in an existing document, it should.

### 5.3 No Schema Before Conceptual Stability

Formal schemas are deferred until:

```text
the substrate role is stable
the object boundary is clear
the lifecycle is understood
the non-collapse laws are known
the implementation target is selected
```

Until then, use minimal object sketches only.

### 5.4 Compression Must Preserve Lineage

Compression may reduce wording, but must not erase:

```text
source concept
original distinction
lineage
scope
non-claims
role in architecture
reason for merge/demotion/archive
```

### 5.5 Compression Must Not Flatten Regime Difference

Do not compress two concepts together just because they are adjacent.

Examples:

```text
projection ≠ source
token ≠ distinction
embedding ≠ meaning
belief ≠ truth
agreement ≠ consent
consent ≠ authority
trust ≠ authority
access ≠ consequence permission
proof ≠ governance
authority ≠ reference
reference ≠ canon
canon ≠ final truth
```

## 6. Attention Budgeting

Conceptual work has finite attention budget.

Attention should be allocated to concepts that:

```text
increase architecture coherence
reduce regime confusion
preserve invariants
clarify implementation path
reduce document sprawl
prevent dangerous collapse
create reusable compression
```

Attention should be reduced for concepts that:

```text
spawn excessive terminology
duplicate existing dynamics
lack a clear location
do not change decisions
create schema churn
create implementation distraction
inflate metaphysical language without operational payoff
```

The workflow must regularly ask:

```text
Is this concept regenerating coherence, or consuming coherence?
```

## 7. Decision Space Navigation

Every architecture change is a decision.

A decision must declare:

```text
available branches
chosen branch
rejected branches
reason for choice
expected consequence
risk of collapse
document affected
concepts preserved
concepts demoted
follow-up required
```

Example:

```text
Decision:
Do we create a standalone Symbolic Regime?

Chosen:
No standalone primary regime yet.

Reason:
Symbolic dynamics are system-wide, but symbolic objects live primarily under Projection / Index / Rasterization.

Preserve:
Symbolic Object Ecology.

Demote:
Symbolic Regime as standalone substrate.

Consequence:
Projection doc must include token / embedding / symbol lifecycle.
```

## 8. Invariant Integration

A concept is integrated only when it preserves or improves invariance.

Integration tests:

```text
Does it preserve the four-substrate model?
Does it clarify read/write topology?
Does it prevent collapse?
Does it improve projection fidelity?
Does it clarify decision/consequence dynamics?
Does it reduce schema pressure?
Does it preserve RIFT primitives?
Does it improve DME architecture?
Does it create implementation traction?
```

If not, defer or archive.

## 10. Documentation Roles

### 10.1 Theory Foundation

Defines what must be preserved.

It should answer:

```text
What is configuration?
What is distinction?
What is attention?
What is identity?
What is memory?
What is projection?
What is proof?
What is consequence?
What is budget?
What is authority?
What is reference?
```

### 10.2 Core Architecture

Defines the skeleton.

It should answer:

```text
What are the four substrates?
How do they relate?
What is the main runtime loop?
What are the major regime ecologies?
```

### 10.3 Read/Write Topology

Defines the dynamic topology.

It should answer:

```text
What is read-side configuration topology?
What is write-side attentional topology?
How do projection, execution, and integrate mediate the loop?
```

### 10.4 Projection / Index / Rasterization

Defines addressability.

It should answer:

```text
How does topology become handles, tokens, embeddings, symbols, packets, dashboards, and LLM-readable views?
```

### 10.5 Operator Grammar

Defines lawful movement.

It should answer:

```text
What operations move structures across substrates and regimes?
What is conserved?
What is lost?
What receipts are required?
```

### 10.6 Runtime Regime Lifecycle

Defines lifecycle dynamics.

It should answer:

```text
How do distinction, belief, decision, intention, consent, execution, consequence, feedback, retention, proof, authority, reference, and canon relate?
```

### 10.7 Glossary / Non-Collapse Laws

Summarizes stabilized terms after the architecture has settled.

It should not be written too early.

## 11. Glossary Timing

The glossary should be written late.

Reason:

```text
A glossary written too early becomes a projection cage.
A glossary written after stabilization becomes retained compression.
```

The glossary should summarize stabilized distinctions rather than force premature language.

## 12. Concept Admission Questions

Before integrating any concept, ask:

```text
1. What distinction does this concept preserve?
2. What substrate does it touch?
3. Is it a regime, lifecycle object, operator, constraint, handle, or example?
4. What existing concept does it refine or replace?
5. What collapse does it prevent?
6. What budget does it deserve?
7. What should be archived or released because of it?
8. Does it require proof now, or only retention?
9. Does it need schema now, or only an object sketch?
10. What is the smallest invariant expression?
```

## 14. Compression Map Discipline

Every major doc rewrite should update or reference the Architecture Compression Map.

The compression map must track:

```text
old doc
new home

mutated concepts
archived/retired concepts
deferred schema
```

## 15. Archive Law

Archiving is not deletion.

A document may be archived when:

```text
its active concepts are merged
its deprecated concepts are marked
its historical role is preserved
its replacement doc is named
```

Archive statuses:

```text
source_preserved
superseded
merged
historical
deprecated
unsafe_to_use
```

## 16. Schema Deferral Law

Formal schemas are expensive.

Do not create schema unless it has:

```text
stable object identity
stable lifecycle
stable non-claims
clear substrate ownership
clear regime participation
implementation need
```

Before that, use:

```text
minimal object anchors
field sketches
example packets
non-claim lists
```
