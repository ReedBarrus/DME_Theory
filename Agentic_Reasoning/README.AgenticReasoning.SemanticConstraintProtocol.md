## 1. Purpose

This document defines the Semantic Constraint Protocol for agentic reasoning.

Semantic constraint is the practice of improving reasoning by explicitly binding language to definitions, distinctions, scope, non-collapse laws, conservation anchors, and admissible transformations.

The purpose is not to restrict thought.

The purpose is to prevent thought from collapsing, drifting, inflating, or hallucinating.

Core law:

```text
Semantic constraint increases intelligence by preserving distinctions under transformation.
```

## 3. What Semantic Constraint Is

Semantic constraint is the deliberate use of:

```text
definitions
scope
status
boundaries
non-claims
non-collapse laws
conservation laws
operator constraints
source references
admissibility checks
authority ceilings
```

It asks:

```text
What does this term mean?
What does it not mean?
What scope does it apply under?
What is it being confused with?
What transformation is occurring?
What must be preserved?
What is being lost?
What consequence follows if we accept this?
```

## 5. The Semantic Constraint Loop

Canonical loop:

```text
Term / Claim / Concept
→ Distinguish
→ Define
→ Scope
→ Locate
→ Compare
→ Non-Collapse
→ Conservation Check
→ Consequence Check
→ Integrate / Revise / Release
```

### Step 1 — Term / Claim / Concept

A new word, claim, concept, metaphor, or object appears.

### Step 2 — Distinguish

Ask:

```text
What is this different from?
What boundary does it introduce?
What problem does it solve?
```

### Step 3 — Define

Create a working definition.

```text
X = ...
```

### Step 4 — Scope

Declare where the definition applies.

```text
Under what context, lens, regime, or use case?
```

### Step 5 — Locate

Place the term in a hierarchy.

```text
Is this a substrate, regime, object, operator, envelope, record, lifecycle dynamic, metric, or metaphor?
```

### Step 6 — Compare

Compare against nearby terms.

```text
How is this different from existing concepts?
Does it duplicate anything?
Does it compress or mutate something?
```

### Step 7 — Non-Collapse

State what it is not.

```text
X ≠ Y
```

### Step 8 — Conservation Check

Ask what must remain preserved across transformations.

```text
What lineage, scope, identity, uncertainty, proof, or authority must be conserved?
```

### Step 9 — Consequence Check

Ask what changes if this term is accepted.

```text
Does it alter architecture?
Does it affect workflow?
Does it create new obligations?
Does it increase or reduce coherence?
```

### Step 10 — Integrate / Revise / Release

Decide whether the concept should be integrated, revised, deferred, quarantined, or released.

## 6. Concept Admission Questions

Before admitting a concept, ask:

```text
1. What is the distinction?
2. What is the definition?
3. What does it not mean?
4. What existing term is closest?
5. Is this concept necessary?
6. Is it root, derived, compound, or metaphorical?
7. What scope does it apply under?
8. What does it preserve?
9. What does it risk collapsing?
10. What docs or workflows would change?
11. What non-collapse laws are needed?
12. Should it be active, deferred, archived, or released?
```

Core law:

```text
No new concept without distinction pressure.
```

## 7. Semantic Constraint Object Classes

### Definition

```text
Definition =
compressed meaning handle for a term under scope.
```

### Scope

```text
Scope =
declared boundary of valid use.
```

### Non-Claim

```text
Non-Claim =
explicit statement of what a term, object, or process does not imply.
```

### Non-Collapse Law

```text
Non-Collapse Law =
boundary equation preventing two related concepts from being treated as identical.
```

Example:

```text
attention ≠ intention
```

### Conservation Anchor

```text
Conservation Anchor =
statement of what must remain preserved across transformation.
```

Example:

```text
Provenance must preserve lineage, lens, loss, scope, and reconstruction conditions.
```

### Authority Ceiling

```text
Authority Ceiling =
limit on what a claim, object, source, or agent may affect as consequence.
```

### Admissibility Condition

```text
Admissibility Condition =
condition under which a term, claim, or transition may proceed.
```

## 8. Non-Collapse Laws as Intelligence Supports

Non-collapse laws prevent reasoning from flattening distinctions.

Examples:

```text
map ≠ territory
projection ≠ source
attention ≠ intention
intention ≠ permission
decision ≠ execution
execution ≠ legitimacy
feedback ≠ proof
proof ≠ authority
authority ≠ truth
reference ≠ canon

```

A non-collapse law does not block relation.

It prevents identity collapse.

Correct posture:

```text
A may relate to B.
A may influence B.
A may support B.
A may transform into B under conditions.
A is not automatically B.
```

## 13. Constraint Failure Modes

### Overconstraint

```text
Too many rules prevent exploration.
```

Symptoms:

```text
premature schemas
no metaphor allowed
every concept blocked
excessive definitions before insight
```

Correction:

```text
return to exploratory distinction generation
```

### Underconstraint

```text
Too few rules allow semantic collapse.
```

Symptoms:

```text
everything becomes everything
terms duplicate
authority leaks
metaphor becomes doctrine
```

Correction:

```text
define, scope, compare, and add non-collapse laws
```

### Misconstraint

```text
Wrong boundary blocks useful relation or preserves the wrong distinction.
```

Symptoms:

```text
false dichotomy
category mistake
unnecessary regime split
overly rigid terminology
```

Correction:

```text
revise hierarchy and relation type
```

## 14. Semantic Constraint Decision Outcomes

After semantic evaluation, a concept may be:

```text
Accept
Revise
Compress
Merge
Defer
Quarantine
Archive
Release
```

### Accept

The concept becomes active.

### Revise

The concept is useful but needs adjustment.

### Compress

The concept becomes part of a larger term.

### Merge

The concept duplicates another and should merge.

### Defer

The concept is useful later but not now.

### Quarantine

The concept is risky, sticky, overloaded, or collapse-prone.

### Archive

The concept preserves lineage but is no longer active.

### Release

The concept is not currently needed.

## 16. Using Non-Collapse Laws During Agent Reasoning

Agents should use non-collapse laws as active reasoning checks before summarizing, editing, implementing, or answering DME-related questions.

Operational pattern:

```text
1. Identify the terms being related.
2. Check whether the relation is support, influence, transformation, containment, or identity.
3. If identity is being implied, verify whether the docs explicitly allow it.
4. Preserve "A may support/influence/transform into B under conditions, but A is not automatically B."
5. Declare loss, uncertainty, and authority ceiling when compressing concepts.
6. Prefer bounded relation over equivalence.
```

Examples:

```text
projection may expose source-derived topology, but projection != source.
attention may pressure intention, but attention != intention.
proof may support authority, but proof != authority.
ledger may preserve provenance, but ledger != truth.
archive may preserve lineage, but archive != active doctrine.
agent request may pressure decision topology, but request != permission.
```
