## 6. Active vs Archive Policy

The repository may contain active documents and archive documents.

### Active Documents

Active documents define current doctrine.

They should be used for:

```text
architecture explanation
conceptual development
future docs
implementation orientation
schema planning
agent memory loading
summary generation
glossary alignment
```

### Archive Documents

Archive documents preserve lineage.

They should be used for:

```text
historical comparison
concept recovery
migration trace
conceptual archaeology
checking what was superseded
```

Archive documents should not be treated as active doctrine unless the user explicitly asks to revive, compare, or restore a concept.

Core law:

```text
Archive is provenance.
Archive is not active authority.
```

## 7. Conflict Resolution Rules

When sources disagree:

### Current repo vs old uploaded file

```text
Prefer current repo.
Use old file only for lineage or comparison.
```

### Current repo vs assistant memory

```text
Prefer current repo.
Assistant memory may be stale.
```

### Current repo vs active user instruction

```text
Follow active user instruction.
Flag if it mutates or overrides current doctrine.
```

### Active doc vs archive doc

```text
Prefer active doc.
Archive doc preserves prior formulation.
```

### Two active docs disagree

```text
Prefer the newer or more specific doc.
If uncertainty remains, ask user or identify the contradiction explicitly.
```

Suggested specificity order:

```text
Glossary for definitions.
SystemWalkthrough for lifecycle example.
Regime ecology docs for regime-specific dynamics.
Substrate docs for substrate-specific mechanics.
CoreArchitecture for high-level architecture.
TheoryFoundation for foundational framing.
ArchiveMigrationMap for lineage.
```

When assisting on DME theory work, the assistant or agent should:

```text
1. Treat https://github.com/ReedBarrus/DME_Theory as canonical active memory.
2. Prefer current non-archived repo files over legacy project uploads.
3. Ask or verify before reviving archived doctrine.

5. Preserve current hierarchy:
   - Root operational regime: Distinction Space
   - Primary runtime coordinates: Agency, Decision
   - Cross-cutting support regimes: Projection, Ledger/Provenance, Retention, Proof,
     Budget/Admissibility, Authority/Reference, Feedback/Integration
   - Derived lifecycle dynamics: Expectation, Belief, Intention, Consent, Execution,
     Consequence, Trust, Access, Repair, Contest, Revocation, Canon
6. Preserve the four-substrate architecture:
   Structure
   Runtime
   Ledger
   Projection / Index / Rasterization
7. Avoid spawning new regimes unless burden requires it.
8. Treat schemas as deferred unless the user explicitly asks for implementation/schema work.
9. Treat archive migration as provenance, not active doctrine.
10. When uncertain, state uncertainty and request the relevant repo file or verify the repository.
```

