## 1. Purpose

This document defines the Projection Ecology of DME V2.

Projection is a cross-cutting support regime.

It governs addressability across:

```text
distinctions
runtime states
agentic observer frames
attention envelopes
commitments
decision envelopes
branch topology
execution candidates
consequence signatures
feedback records
integrated consequence records
retention echoes
proof traces
authority constraints
reference candidates
ledger provenance topology
```

Projection answers:

```text
What can be addressed?
What can be made visible?
What can be queried?
What can be selected?
What can be symbolized?
What can be rasterized?
What can be compared?
What can be routed?
What handles are allowed?
What handles are blocked?
What loss must be declared?
What access is permitted?
What authority ceiling applies?
```

Projection is not merely display.

Projection is governed addressability.

---

## 2. Core Thesis

```text
Projection Ecology is the regime of governed addressability:
what topology can be made visible, queryable, selectable, symbolized, routed,
and acted upon through controlled handles.
```

Compressed:

```text
Runtime produces active topology.
Ledger conserves provenance topology.
Projection makes topology addressable.
Index stabilizes retrieval and coordinate access.
Rasterization renders topology into usable views, packets, symbols, and handles.
```

Core law:

```text
Projection makes topology addressable.
Projection does not become the topology it addresses.
```

---

## 3. Why Projection Exists

DME topology is not useful if it cannot be addressed.

Agents, humans, tools, dashboards, and workflows require projected surfaces.

But projection is dangerous because making something addressable changes attention, access, salience, and possible consequence.

Without Projection Ecology, DME risks collapse such as:

```text
projection → source
handle → topology
view → reality
token → distinction
embedding → meaning
dashboard → truth
visibility → permission
access → authority
salience → support
summary → full context
```

Projection Ecology prevents these collapses by preserving source refs, provenance, lens, loss, scope, uncertainty, access boundary, authority ceiling, and allowed/blocked response handles.

## 4. Projection

### Definition

```text
Projection =
bounded rasterization of topology into addressable view-space.
```

Projection makes selected topology available as:

```text
handle
view
token
symbol
embedding region
dashboard
agent read packet
governance packet
decision map
query result
summary
alert
interface element
```

Projection is always a transformation.

Projection must declare what it exposes, hides, compresses, omits, or distorts.

### Non-Claims

```text
projection ≠ source
projection ≠ topology
projection ≠ truth
projection ≠ proof
projection ≠ authority
projection ≠ full context
```

## 5. Addressability

### Definition

```text
Addressability =
capacity for topology to be referenced, queried, selected, compared, routed,
or acted upon through a projection handle.
```

Addressability is not access by itself.

It is the possibility of reference.

Access determines who/what may use the address.

Admissibility determines what movement may proceed through it.

Authority determines what consequence may be affected through it.

### Non-Claims

```text
addressability ≠ access
addressability ≠ authority
addressability ≠ permission
addressability ≠ execution
```

## 34. Relationship to Other Documents

### Projection / Index / Rasterization Substrate

Defines the substrate surface of projection, indexing, rasterization, handles, symbols, views, and addressability.

### Runtime Regime Lifecycle

Defines Projection Space as the support regime answering:

```text
What can be addressed?
```

### Distinction Ecology

Projection makes distinctions addressable without turning them into tokens, truth, or symbols by default.

### Agency Ecology

Projection provides ObserverFrames, ProjectionAccessProfiles, AttentionEnvelopes, AgentReadPackets, and response handles.

### Decision / Consequence Ecology

Projection makes decision topology navigable through branch maps, simulations, expected consequence views, and decision dashboards.

### Budget / Admissibility Ecology

Projection requires constrained transition logic because visibility creates attention pressure and possible consequence paths.

### Feedback / Integration Ecology

Feedback updates projection fidelity, lens, loss, allowed handles, salience, retention posture, and authority implications.

### Retention Ecology

Projection artifacts can persist, echo, decay, archive, quarantine, or release; retained projections must preserve loss and valid use.

### Ledger / Provenance Ecology

Ledger records projection history when projection affects attention, decision, access, consequence, retention, authority, or reference.

### Proof Ecology

Proof can require projection, but projected proof artifacts are not proof by themselves.

### Authority / Reference Ecology

Authority and reference need projection surfaces, but projection never grants authority or canonizes reference by itself.
